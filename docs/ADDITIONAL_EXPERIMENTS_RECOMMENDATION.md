# PEAC 논문 비판에 대한 추가 실험 가이드

**목적:** 리뷰어 비판(한계점·개선점·추가사항)에 대해, **추가 실험이 필요한지**와 **한다면 어떻게 할지**를 정리. 논문 텍스트 수정은 별도.

---

## 1. 추가 실험이 꼭 필요한가?

- **필수는 아님.** 현재 논문만으로도 "정적 사전 필터가 지연/가용성에 도움된다"는 주장은 실험으로 뒷받침됨.
- **하지만** 비판 내용 중 상당수는 "한계를 인정하고, 실험으로 보여주거나 개선 방향을 제시"하면 논문이 훨씬 설득력 있어짐.
- 따라서 **일부만 선별해 추가 실험**하는 것을 권장. 아래는 비판 항목별로 "실험 필요 여부"와 "구체적 방법"을 정리한 것.

---

## 2. 비판 항목별 실험 필요성 및 방법

### 2.1 동적 실행 기반 공격 탐지의 한계 (정적 지표만 사용)

**비판:** 복잡한 동적 실행 경로를 거쳐야만 탐지되는 공격은 원천적으로 방어 불가.

**추가 실험 필요성:** **선택(권장).**  
- "한계"를 **실험으로 보여주면** Discussion/Limitations 절이 강해짐.  
- 실험이 없어도 "우리는 정적 지표만 사용하며, 동적 경로 기반 공격은 본 방어의 범위 밖이다"라고 명시하면 됨.

**한다면 어떻게:**

| 단계 | 내용 |
|------|------|
| 1 | **동적 할당만 유발하는 트랜잭션** 1종 설계. 예: 스토리지 값에 따라 반복 횟수가 정해지는 루프에서 대량 할당, calldata/gas_limit/access_list는 정상 범위로 유지. |
| 2 | 해당 tx를 **PEAC(현재 정적 필터)로는 거절되지 않음**을 확인. |
| 3 | Vanilla vs PEAC 동일 환경에서 해당 tx를 혼합한 워크로드 실행 → **P99 지연 또는 GC 이벤트 수**가 PEAC에서도 크게 증가함을 측정. |
| 4 | 결과를 "정적 필터만으로는 이 유형의 공격을 완화하지 못함"으로 기술. |

**필요 자원:** 스마트 컨트랙트 1개 + tx 생성 스크립트. 현재 caliper/hardhat 인프라 확장.

---

### 2.2 MEV 기회 상실

**비판:** 노드 단위 로컬 거절로 인해 Proposer의 MEV 후보 풀이 줄어드는 경제적 단점.

**추가 실험 필요성:** **낮음.**  
- 논문에서 이미 "선택적 해제"를 권장하고 있어, 정성적 대응은 되어 있음.  
- **실험으로 보여주려면:** MEV 유사 트랜잭션(스왑/차익거래 패턴) 비율을 정의한 뒤, 현재 θ 설정에서 그 중 얼마가 거절되는지 측정하는 정도.  
- 이건 **새 메트릭(MEV-like tx 비율, 거절률)** 정의가 필요하고, 실험 복잡도 대비 논문 이득은 상대적으로 작음.  
- **권장:** 실험보다는 Discussion에서 "MEV 후보 감소 가능성과 선택적 필터 해제"를 1~2문단으로 명확히 적는 쪽이 효율적.

---

### 2.3 운영자 설정 의존성 및 오탐(False Positive) 위험

**비판:** θ, τ를 운영자가 수동 설정하면, 잘못된 설정 시 합법적인 high-gas / low-value 트랜잭션이 공격으로 오인되어 거절될 수 있음.

**추가 실험 필요성:** **높음(강력 권장).**  
- 리뷰어가 구체적으로 지적한 부분이고, **현재 인프라만으로 구현 가능.**

**한다면 어떻게 (임계값 민감도 실험):**

| 단계 | 내용 |
|------|------|
| 1 | **"정상" 워크로드** 정의. 예: 화이트리스트에 넣지 않은, high-gas low-value 스마트 컨트랙트 호출(예: 특정 DEX/오라클 호출 유사). 현재 bloat(100), 15M gas와 구분되는, "합법적으로 허용하고 싶은" 패턴. |
| 2 | **θ에 해당하는 파라미터**를 여러 값으로 설정. 예: `BAN_HEAVY_GAS_LIMIT` = 8M, 10M, 12M, 15M, 20M. (현재 10M 사용 중이라면 그 주변으로.) |
| 3 | 각 θ에 대해 **동일한 정상 워크로드**를 PEAC 적용 노드로 보냄. |
| 4 | **성공률(또는 거절률)**을 θ별로 기록. 예: "θ=10M에서 정상 tx 0% 거절, θ=8M에서 5% 거절" 등. |
| 5 | (선택) **공격 워크로드**도 동일 θ들에 대해 실행해, θ가 낮을수록 방어는 강해지지만 정상 tx 오탐이 늘어남을 표/그래프로 정리. |

**필요 자원:**  
- 현재 `ban_proxy`의 `BAN_HEAVY_GAS_LIMIT`(및 필요 시 위험 점수 임계값)만 바꾸는 실험.  
- 정상 워크로드 1종만 정의하면 됨(기존 hardhat/run_phases_node.js 스타일로 추가 가능).

**기대 결과:**  
- "θ 선택에 따라 오탐이 발생할 수 있음"을 정량적으로 보여줌.  
- "자동 임계값 조정(추가 실험/향후 연구)"로 자연스럽게 이어짐.

---

### 2.4 정적 오프라인 선형 회귀 모델의 한계

**비판:** 가중치 w_i가 오프라인 프로파일링·선형 회귀로만 도출되어, 런타임/네트워크 변화나 새로운 공격 패턴에 유연히 대응하기 어렵다.

**추가 실험 필요성:** **중간(권장).**  
- "고정 가중치의 한계"를 **실험으로 보여주면** 설득력 증가.

**한다면 어떻게 (공격 패턴 변경 실험):**

| 단계 | 내용 |
|------|------|
| 1 | **현재와 다른 공격 혼합** 설계. 예: calldata는 작게, **access_list 크기만 크게** / **contract creation 비중을 높인** 워크로드. (현재는 bloat(100), 15M gas 위주.) |
| 2 | **동일 θ(동일 PEAC 설정)**로 위 워크로드 실행. |
| 3 | **기존 실험(bloat 100, 15M gas)** 대비 (a) P99 개선 폭이 줄어드는지, (b) GC 이벤트/시간 감소 폭이 작아지는지 측정. |
| 4 | 해석: "프로파일링된 패턴과 다른 혼합에서는 동일 가중치·동일 θ로도 효과가 제한적일 수 있음" → 적응형 가중치/자동 튜닝의 필요성으로 연결. |

**필요 자원:**  
- 기존 인프라 유지. Hardhat에서 **다른 bloat/access_list/contract creation 비율**의 시나리오 1~2개 추가.

---

### 2.5 자동화된 임계값 조정 / 머신러닝 기반 동적 가중치

**비판:** θ, τ를 트래픽·리소스 상태에 따라 자동 조정해야 함; w_i를 GC·힙 상태 피드백으로 동적 조정해야 함.

**추가 실험 필요성:** **선택(향후 연구).**  
- 이건 **시스템 개선**이므로, "추가 실험"이라기보다 **새 기안 + 구현 + 실험**에 가까움.  
- 단기 리비전에서는 **실험보다는 "한계 인정 + 향후 작업"**으로 적는 것이 현실적.  
- 나중에 간단한 자동 조정(예: P99 목표치 두고 θ를 주기적으로 상/하 조정)을 구현하면, 그때 "자동 θ 실험"을 추가할 수 있음.

---

### 2.6 화이트리스트 자동화 / 피처 벡터 확장

**비판:** 화이트리스트를 프로토콜/온체인 정보로 자동 관리해야 함; 서명 복잡도·발신자 과거 성향 등 피처 확장 필요.

**추가 실험 필요성:** **낮음.**  
- 화이트리스트 자동화는 설계·프로토콜 논의 성격이 크고, 현재 caliper/Besu/Nethermind 스트레스 테스트만으로는 한계가 있음.  
- 피처 확장은 **가능하면** 1~2개 피처(예: sender의 과거 평균 gas 사용)를 넣어서 재프로파일링 후, 기존 공격 워크로드에서 성능 비교하는 정도.  
- 우선순위는 2.3(임계값 민감도), 2.4(공격 패턴 변경)보다 낮게 두어도 됨.

---

## 3. 실험 우선순위 요약

| 우선순위 | 비판 항목 | 실험 내용 | 난이도 | 현재 인프라 활용 |
|----------|-----------|-----------|--------|-------------------|
| **1** | 운영자 설정 의존성 / 오탐 위험 | **θ(임계값) 민감도:** 정상 워크로드 + 여러 θ에서 성공/거절률 측정 | 낮음 | 그대로 가능 |
| **2** | 정적 선형 회귀 한계 | **공격 패턴 변경:** 다른 calldata/access_list/creation 비율로 효과 감소 보이기 | 중간 | 시나리오만 추가 |
| **3** | 동적 공격 한계 | **동적 할당 공격 1종:** 정적 필터 통과하지만 실행 시 GC 스파이크 → 방어 불가 정량화 | 중~높음 | 컨트랙트+스크립트 추가 |
| (선택) | MEV | MEV 유사 tx 거절률 측정 | 중간 | 메트릭/정의 필요 |
| (선택) | 피처 확장 | 새 피처 1~2개 추가 후 재평가 | 중간 | 프로파일링·파이프라인 확장 |

---

## 4. 바로 착수 가능한 실험: θ 민감도 (2.3)

**목표:** "θ를 잘못 설정하면 정상 트랜잭션이 거절된다"를 숫자로 보여주기.

**최소 구현:**

1. **정상 워크로드 정의**  
   - 예: gas limit 12M 이하, calldata/access_list는 보통 수준인 "허용하고 싶은" 호출.  
   - 기존 `run_phases_node.js` 또는 동일 포맷의 새 스크립트로 전송.

2. **변수:** `BAN_HEAVY_GAS_LIMIT` = 8M, 10M, 12M, 15M, 20M (또는 위험 점수 θ에 매핑되는 파라미터).

3. **측정:** 각 설정에서 (성공 tx 수 / 전송 tx 수), 필요 시 P99.

4. **정리:** 표 또는 그래프 1개.  
   - "θ=10M: 정상 워크로드 0% 거절; θ=8M: 5% 거절; …"  
   - Discussion에서 "오탐 위험을 줄이기 위해 자동 임계값 조정이 필요함"으로 연결.

이 실험만 추가해도 리뷰어 비판 2.3에 대한 실험적 답변이 가능하고, 나머지 한계는 Discussion에서 인정 + 향후 연구로 정리할 수 있음.

---

## 5. 정리

- **추가 실험을 "반드시" 할 필요는 없지만,**  
  **θ 민감도 실험(2.3)**은 구현이 쉽고 비판과 직접 연결되므로 **강하게 권장.**  
- **공격 패턴 변경(2.4)**은 부담이 크지 않으면 권장.  
- **동적 공격 한계(2.1)**는 시간이 있으면 하면 좋고, 없으면 "한계"를 텍스트로만 명시해도 됨.  
- MEV, 자동 θ/가중치, 화이트리스트·피처 확장은 **논문 수정 시** "Limitations & Future Work"에 넣고, 실험은 선택 또는 후속 연구로 두면 됨.

논문 수정은 나중에 하신다고 하셨으므로, 위 우선순위를 참고해 **실험만 먼저 설계/실행**하시면 됨.
