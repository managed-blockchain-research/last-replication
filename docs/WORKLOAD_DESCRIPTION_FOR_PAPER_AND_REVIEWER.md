## 1. 리뷰어에게 넣을 답변 (Rebuttal용)

**Q: What transaction mix? Replay trace? Synthetic workload?**

We thank the reviewer for this important clarification. Our evaluation uses a **synthetic, single-type workload**, not mainnet trace replay.

- **Transaction type:** Every transaction is a single contract call to a **state-bloating** function: `bloat(startIndex, count)`, which writes to `count` distinct storage slots in a dedicated Solidity contract (StateBloater). There is no mix of transfer, DEX, or other on-chain operations.
- **Replay trace?** **No.** We did not use any recorded mainnet or testnet trace. The workload is generated by a parameterized driver (multi-threaded clients) that repeatedly invokes this contract with fixed parameters per run.
- **Synthetic workload?** **Yes.** The workload is synthetic and designed to induce **controlled allocation pressure** on the managed runtime: each transaction triggers a predictable amount of state-trie and in-memory activity (storage writes and Merkle-path updates), which we use to reproducibly cross the Latency Cliff threshold (Section X) and compare Baseline vs. LASS under the same load.
- **Rationale:** Our goal is to isolate and measure the effect of LASS on GC-driven latency under **repeatable, comparable conditions**. A single-type synthetic workload ensures that any difference in latency and GC metrics is attributable to LASS rather than to variation in transaction mix. We acknowledge that mainnet trace replay or mixed workloads would better reflect production diversity; we have added a short subsection (Section X) and a limitation in the revised manuscript and suggest trace replay as future work.

## 2. 논문에 넣을 "Workload" 문단 (Experimental Setup 보강)

아래를 **Evaluation / Experimental Setup**에 "Transaction Workload" 또는 "Workload Design" 소절로 추가하면 됩니다.

---

**Transaction Workload.**  
We use a **synthetic, single-type workload** (no mainnet or testnet trace replay). Each transaction is one contract call to a state-bloating function `bloat(startIndex, count)` in a dedicated Solidity contract, which writes to `count` distinct storage slots and induces Merkle-trie updates and allocation in the client. The driver runs multiple worker threads that repeatedly submit such transactions with no rate limiting (maximum sustained throughput). Parameters are fixed per run: e.g., Besu runs use 20 workers and 200 storage slots per transaction for 600 seconds; Nethermind runs use 14 workers and 300 slots per transaction for 600 seconds. This design gives a **controlled, repeatable** allocation rate so that Baseline and LASS are compared under identical load and any difference in GC and latency is attributable to LASS. We do not claim that this workload represents a realistic transaction mix; trace replay or mixed workloads are left as future work.

**Block production and reported latency.**  
Execution is block-based; we report **per-transaction confirmation latency** (time from submit to inclusion in a block), not block-level processing latency. Under sustained load, block producers pack and seal blocks at the chain’s block interval (e.g. ~1 s for our Besu dev network); the **mean transactions per block** is therefore approximately equal to sustained throughput in tx/s (e.g. **~109–114 for Besu**, **~198–209 for Nethermind** in the reported runs).

## 5. "How many transactions per block?" — 리뷰어 추가 질문 대비

리뷰어가 자주 묻는 이유: Ethereum 실행은 **블록 단위**, latency도 block processing 관점에서 다루기 때문인데, 현재 설명은 **트랜잭션 생성기(드라이버)** 기준이라 블록 단위 정보가 없음.

### 5.1 리뷰어 답변용 문단 (Rebuttal에 추가)

**Q: How many transactions per block?**

Thank you for raising this. We clarify the following:

- **Latency we report** is **per-transaction confirmation latency** (time from the client submitting a transaction until it is included in a block and we observe confirmation), not block processing latency. So the P50/P95/P99 in the paper are **transaction-level** end-to-end latencies.
- **Block-level behavior:** Execution is block-based. The driver submits transactions continuously at maximum rate; the node’s block producer packs and seals blocks. So the number of transactions per block is determined by (1) block interval and (2) sustained throughput. In our setup:
  - **Besu (dev network):** Block production is effectively **1 block per second**. With sustained throughput ~109–114 tx/s (Baseline vs LASS), the **mean number of transactions per block is ~109–114** (e.g. ~109 Baseline, ~114 LASS).
  - **Nethermind (dev):** Similarly, with **~198–209 tx/s** sustained, and block interval on the order of 1 second, **mean transactions per block is ~198–209**. (If the test used a chain with a different block interval, one can state it and give mean tx/block = throughput / blocks_per_second.)
- We have added a short sentence in the revised manuscript (Section X): “Under the reported sustained throughput and block interval (e.g. 1 s for Besu dev), the mean transactions per block is approximately equal to throughput in tx/s (~109 for Besu, ~200 for Nethermind).”

(실제 실험이 다른 block interval을 쓰면, 해당 값을 넣고 `mean tx/block = throughput_tx_per_sec / blocks_per_sec` 로 계산해 넣으면 됩니다.)

### 5.2 논문에 넣을 한두 문장 (Workload 문단 뒤에 추가)

**Block production and transactions per block.**  
Execution is block-based; we report **per-transaction confirmation latency** (submit to inclusion), not block processing latency. The driver submits at maximum rate; the node’s block producer packs and seals blocks. For our dev networks (e.g. block interval ≈ 1 s for Besu), the **mean transactions per block** under sustained load equals throughput in tx/s—e.g. **~109–114 tx/block** for Besu and **~198–209 tx/block** for Nethermind in the reported runs.
